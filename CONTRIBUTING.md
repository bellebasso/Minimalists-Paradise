## Project Structure

This project uses a modular CSS structure in the `src/` directory. All styles are bundled together into the root `theme.css` during the build process.

> [!IMPORTANT]
> **Do not edit `theme.css` directly.** This file is automatically generated and overwritten whenever the build script runs. All modifications should be made within the modular CSS files inside the `src/` folder.

- **`src/`**: Contains the source modular CSS files.
  - **`index.css`**: The entry point. Contains the Style Settings configuration headers at the top, and `@import` rules at the very bottom.
  - **`foundation/`**: Contains base variables, global styles, and typography.
  - **`app/`**: Contains workspace layout, modals, and mobile-specific styles.
  - **`features/`**: Contains UI elements, snippets (like Hider), and frosted glass effects.
  - **`plugins/`**: Contains styling overrides for third-party Obsidian plugins (e.g. Kanban).
- **`scripts/`**: Development, bundling, linting, and synchronization scripts.
- **`manifest.json`**: Theme metadata (name, version, minObsidianVersion) used by Obsidian.

## Getting Started

To set up your local development environment:

1. **Fork and Clone the Repository**
   ```bash
   git clone https://github.com/YOUR-USERNAME/Minimalists-Paradise.git
   cd Minimalists-Paradise
   ```

2. **Install Dependencies**
   This installs the development dependencies and automatically configures Husky hooks.
   ```bash
   npm install
   ```

3. **Configure Your Environment**
   Copy the example environment file:
   ```bash
   cp .env.example .env
   ```
   Open the `.env` file and set the `OBSIDIAN_VAULT_PATH` variable to the absolute path of your local Obsidian vault:
   ```env
   OBSIDIAN_VAULT_PATH="/Users/yourusername/Documents/MyObsidianVault"
   ```
   *Note: This path is used by the synchronization script to copy the output files directly into your active vault for real-time testing.*

## Development Workflow

### Real-Time Development (`npm run dev`)
To edit the theme and see your changes instantly inside Obsidian:
1. Run the development command:
   ```bash
   npm run dev
   ```
2. This script watches for any changes in `src/**/*.css` and `manifest.json`.
3. Whenever a change is detected, it automatically rebuilds the theme (`npm run build`) and copies the output (`theme.css` and `manifest.json`) into the themes directory of your configured Obsidian vault (`npm run sync`).

### Building and Verifying (`npm run build`)
Before committing or creating a pull request, run a full build verification:
```bash
npm run build
```
This runs the complete pipeline:
1. **Bundling**: Bundles modular source files into a single `theme.css` (`scripts/bundle.js`).
2. **Merging**: Merges duplicate CSS selectors (`scripts/merge-duplicates.js`).
3. **Linting**: Lints the CSS rules (`stylelint`).
4. **Validation**: Verifies styling compliance via the checklist (`scripts/css-checklist.js`).

## NPM Scripts Reference

| Script | Command / Tool | Description |
| :--- | :--- | :--- |
| `npm run dev` | `chokidar` + build + sync | Watches `src/` and `manifest.json` and syncs changes to your vault. |
| `npm run build` | bundle + merge + lint + check | Compiles, optimizes, and verifies the complete stylesheet. |
| `npm run bundle` | `scripts/bundle.js` | Bundles CSS modular files from `src/index.css` to `theme.css`. |
| `npm run sync` | `scripts/sync-to-obsidian.sh` | Synchronizes the built theme files to the target Obsidian vault. |
| `npm run css:merge` | `scripts/merge-duplicates.js` | Combines duplicate selectors using PostCSS to reduce stylesheet size. |
| `npm run css:check` | `scripts/css-checklist.js` | Scans for styling issues (e.g. `!important`, duplicate selectors, `:has()`). |
| `npm run lint` | `stylelint` | Validates CSS against project Stylelint guidelines. |
| `npm run lint:fix` | `stylelint --fix` | Automatically fixes style violations where possible. |
| `npm run release` | `npm version patch ...` | Increments version (patch) and commits with conventional version message. |

## Coding Standards

We follow strict styling standards to ensure the theme remains clean, fast, and easy to maintain.

### CSS Style Rules
Our Stylelint configuration (`.stylelintrc.json`) enforces standard rules:
- **No Duplicate Selectors**: All styling for a selector should be grouped together. Duplicates are also consolidated by PostCSS when building.
- **Long Hex Values**: Always use long-form hex codes (e.g., `#ffffff` instead of `#fff`).
- **No Descending Specificity Warnings**: Structure rules properly so that later rules do not have lower specificity than earlier rules.

### CSS Checklist Validation (`npm run css:check`)
The checklist script inspects source files and flags:
- **`!important` declarations**: Avoid using `!important` unless absolutely necessary to override Obsidian defaults.
- **`:has()` pseudo-class**: Keep track of `:has()` usages for compatibility reviews.
- **Duplicate Selectors in source files**: Keeps the source clean and structured.

> This is important to comply with Obsidian's theming best practices.

## Commit Guidelines

We use **Conventional Commits** to keep a clear git history. A Husky hook validates your commit messages automatically upon commit.

The commit message format should be:
```
<type>(<scope> - optional): <description>
```

### Common Types:
- `feat`: A new feature (e.g., `feat(headers): add style options for h3`)
- `fix`: A bug fix (e.g., `fix(tabs): fix active tab border overlap`)
- `docs`: Documentation updates (e.g., `docs: update CONTRIBUTING.md`)
- `style`: Changes that do not affect code logic (white-space, formatting, linting fixes)
- `refactor`: Code restructuring that neither fixes a bug nor adds a feature
- `chore`: Maintenance tasks or dependency updates (e.g., `chore: bump postcss`)

## Submitting a Pull Request

1. Create a new branch for your feature or bug fix:
   ```bash
   git checkout -b feature/my-feature-name
   ```
2. Make your changes in the modular files inside `src/`.
3. Verify your changes pass all tests and linting:
   ```bash
   npm run build
   ```
4. Commit your changes using Conventional Commits.
5. Push to your branch and open a Pull Request against the `main` branch.
